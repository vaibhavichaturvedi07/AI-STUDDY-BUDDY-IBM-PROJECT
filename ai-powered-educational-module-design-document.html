System Architecture Overview

The Study Buddy backend is a modular FastAPI application where every AI-powered feature is encapsulated in its own route module backed by a dedicated service layer. The six educational capabilities are independent — they can be deployed, scaled, and tested separately — yet share a common AI provider abstraction, a single PostgreSQL database, and one JWT-authenticated request context.

Module 1 — PDF Summarization

Purpose

When a user uploads a document (PDF, DOCX, TXT, or Markdown), the system automatically extracts its text content and asks the AI to produce a human-readable summary and a list of key concepts. This gives learners an instant overview before reading the full material.

Data Flow

POST /documents/upload
→
save_upload()
→
Document{status=pending}
→
BackgroundTask
→
extract_text()
→
summarize_document()
→
Document{status=ready}

Text Extraction — document_service.py

Supported Formats

  • PDF — pypdf.PdfReader, page-by-page, double-newline join
  • DOCX — python-docx, paragraph join, page estimate at 300 wds/page
  • TXT / MD — direct Path.read_text() with UTF-8 + error replace

Return Contract

extract_text(file_path, file_type)
  → (raw_text: str,
     word_count: int,
     page_count: int)

Stored on Document.raw_text, .word_count, .page_count

Chunking Strategy

chunk_text(text, max_words=3000) splits long documents on paragraph boundaries before sending to the AI, ensuring the prompt always fits within the model's context window. Each call to summarize_document() receives at most the first 8,000 characters of raw_text.

AI Prompt — summarize_document(text, style)

StyleInstruction sent to LLM
concise2–3 paragraph summary of main points (default)
detailedThorough coverage of all major topics and arguments
bullet_pointsOrganised bullet points grouped by topic

The model is instructed to respond exclusively with a JSON object. The _extract_json() helper strips optional markdown fences and parses the result:

# Expected LLM response
{
  "summary": "...",
  "key_concepts": ["Newton's laws", "inertia", "momentum"]
}

API Endpoints

MethodPathDescription
POST/documents/uploadUpload file; processing runs in background
GET/documents/{id}Poll until status == "ready"
POST/documents/{id}/summarizeRe-generate with a different style
POST/documents/{id}/reprocessRe-run full extraction + summarization
Background isolation. The background task uses its own AsyncSessionLocal() session — not the request-scoped session — to avoid lifetime issues when the HTTP response has already been sent.

Module 2 — Flashcard Generation

Purpose

The AI distills a document into study cards: a front face (question or term), a back face (answer or definition), and an optional hint. Cards are stored in a deck linked to the source document and support SM-2 spaced repetition for intelligent review scheduling.

Generation Flow

POST /flashcards/generate
→
Verify doc.status == ready
→
generate_flashcards(text, n)
→
FlashcardDeck + n×Flashcard
→
201 FlashcardDeckOut

AI Prompt — generate_flashcards(text, num_cards)

The LLM is asked to return a JSON array where each element follows this schema:

[
  {
    "front": "What is Newton's second law?",
    "back": "F = ma — force equals mass times acceleration",
    "hint": "Think about what changes when you push harder"
  }
]

SM-2 Spaced Repetition

Every card carries four SM-2 tracking fields. After each review session, POST /flashcards/cards/{id}/review updates them using the original Anki/SuperMemo-2 algorithm:

Card Fields (DB)

  • ease_factor — starts at 2.5, floored at 1.3
  • interval_days — days until next review
  • repetitions — consecutive successful reviews
  • next_review — scheduled UTC datetime
  • last_reviewed_at — timestamp of last review

Quality Grades (0–5)

  • 0 — Complete blackout → reset interval to 1
  • 1–2 — Wrong → reset repetitions to 0
  • 3 — Correct but hard effort
  • 4 — Correct with hesitation
  • 5 — Perfect → max interval growth
# SM-2 update logic (flashcards.py)
if q >= 3:
    new_ef = ease_factor + (0.1 - (5 - q) * (0.08 + (5 - q) * 0.02))
    card.ease_factor   = max(1.3, new_ef)
    card.interval_days = max(1, round(interval_days * ease_factor))
    card.repetitions  += 1
else:
    card.interval_days = 1
    card.repetitions   = 0
card.next_review = now + timedelta(days=card.interval_days)

Module 3 — Quiz Creation & Auto-Scoring

Purpose

The system generates multiple-choice quizzes directly from uploaded document text at three difficulty levels (easy / medium / hard). Student answers are graded instantly in the backend — not the browser — and every attempt is persisted for progress tracking.

Generation Flow

POST /quizzes/generate
→
doc.status == ready?
→
generate_quiz(text, n, diff)
→
Quiz{questions: JSON}
→
201 QuizOut

Question Schema (stored as JSON column)

{
  "id": 1,
  "question": "Which law states F = ma?",
  "options": ["Newton's 1st", "Newton's 2nd", "Newton's 3rd", "Hooke's Law"],
  "correct_answer": 1,   // 0-based index
  "explanation": "F = ma defines the second law of motion."
}

Auto-Scoring Engine — POST /quizzes/{id}/submit

The route receives a flat array of zero-based choice indices (one per question). It iterates the stored questions, compares each submitted index against correct_answer, and builds a detailed per-question result:

for i, q in enumerate(questions):
    is_correct = payload.answers[i] == q["correct_answer"]
    details.append(QuizResultDetail(
        question_id    = q["id"],
        your_answer    = payload.answers[i],
        correct_answer = q["correct_answer"],
        is_correct     = is_correct,
        explanation    = q.get("explanation", ""),
    ))
score = (correct / len(questions)) * 100

QuizSubmitResult fields

  • score — 0–100 float
  • correct / total — counts
  • passed — score ≥ 60 (configurable)
  • results — per-question detail list
  • attempt_id — UUID of persisted attempt

QuizAttempt (DB)

  • quiz_id / user_id
  • answers[] — submitted indices
  • score / correct_answers
  • time_taken_seconds
  • completed_at — UTC timestamp

Module 4 — Personalized Recommendations

Current Implementation (Data-Driven)

Recommendations are generated by the analytics engine from real usage data — no separate LLM call is required. The system identifies weak areas algorithmically from QuizAttempt scores and StudySession time distributions, then surfaces actionable next steps.

Signal Sources

SignalSource TableHow It's Used
Quiz scores per documentquiz_attempts → quizzesDocuments with avg score < 60% are flagged as weak topics
Flashcard ease factorsflashcards.ease_factorCards at 1.3 (minimum) indicate persistent difficulty
SM-2 review queue depthflashcards.next_review ≤ now()Large due queues = neglected material
Study session frequencystudy_sessions.created_atStreak breaks = topics not revisited
Document processing ratedocuments.statusUnprocessed docs = unused learning material

Recommendation Logic (in analytics.py)

The GET /analytics/summary endpoint returns a top_documents list ranked by activity (quiz count + deck count + avg score). This list is the primary recommendation surface. The frontend presents it as "Most Active Documents" and "Needs Attention" based on score thresholds:

# In analytics.py — top documents ranked by engagement
top_docs = await _top_documents(uid, db, limit=5)

# DocumentStat schema
{
  "document_id": "uuid",
  "title": "Physics Notes",
  "quiz_count": 3,
  "deck_count": 1,
  "avg_quiz_score": 54.2    // below 60 → recommend review
}

Extension Point — AI Recommendations

To add LLM-powered personalized study plans, inject an explain_concept() call referencing the weak document's key_concepts field:

# Proposed future endpoint: POST /analytics/recommendations
weak_docs = [d for d in top_docs if d.avg_quiz_score < 60]
for doc in weak_docs:
    plan = await explain_concept(
        concept=f"Study plan for: {doc.title}",
        context=doc.raw_text[:2000]
    )
    recommendations.append({"doc": doc.title, "plan": plan})
SM-2 is itself a recommendation engine. The GET /flashcards/{deck_id}/due endpoint returns exactly the cards that need attention right now, ranked by overdue interval. This is automatically personalised — no prompt engineering required.

Module 5 — Tutor-Style Chatbot

Purpose

The AI tutor provides a conversational interface where students ask questions in natural language and receive explanations, worked examples, and follow-up prompts. Sessions can be anchored to a specific uploaded document so the AI grounds its answers in the student's actual study material.

Session Architecture

ChatSession (DB)

  • id — UUID
  • owner_id → User (CASCADE)
  • document_id → Document (nullable, SET NULL)
  • title — auto-set or user-named
  • messages[] — ordered by created_at

ChatMessage (DB)

  • role — user | assistant | system
  • content — full text
  • tokens_used — for cost tracking
  • created_at — UTC timestamp
  • Index on (session_id, created_at)

Message Flow — POST /chat/sessions/{id}/messages

User message
→
Load session history (last 10)
→
Load doc.raw_text (if linked)
→
chat_with_tutor()
→
Persist user + AI messages
→
ChatMessageOut

Document Context Injection

When a session has a document_id, the route loads document.raw_text and passes the first 4,000 characters to chat_with_tutor() as document_context. The system prompt becomes:

"You are a friendly, knowledgeable AI study tutor. "
"... "
"The student is studying the document excerpted below. "
"Use it as your primary reference when answering.\n\n"
"--- DOCUMENT CONTEXT ---\n{raw_text[:4000]}\n--- END CONTEXT ---"

Multi-Turn History

The last 10 messages (5 turns) are loaded from the database and included in the prompt. For OpenAI, they are formatted as a structured messages[] array. For watsonx, they are flattened into a single text block with [USER] / [ASSISTANT] role tags, since the watsonx SDK uses a single-string prompt format.

Streak Calculation Algorithm

# _compute_streak() in analytics.py
unique_days = sorted(set(session.date() for session in sessions), reverse=True)

current = 0
if unique_days[0] >= today - timedelta(days=1):
    current = 1
    for i in range(1, len(unique_days)):
        if (unique_days[i-1] - unique_days[i]).days == 1:
            current += 1
        else:
            break

Weak-Topic Detection

Weak topics emerge from two signals that are already captured in the database:

Signal 1 — Quiz Score by Document

Each QuizAttempt links back through Quiz.document_id. The DocumentStat.avg_quiz_score field in top_documents gives a per-source-material average. Any document whose average score falls below 60% is a candidate weak topic.

Signal 2 — Flashcard Ease Factor

Cards stuck at ease_factor == 1.3 (the SM-2 floor) have been answered incorrectly repeatedly. A GET /flashcards/{deck_id}/due call with filter ease_factor ≤ 1.5 reveals exactly which concepts the student struggles with.

Study Session Tracking

StudySession rows are created by the frontend at the start of each learning activity (quiz, flashcard review, chat) and closed with a duration when the activity ends. This populates activity_heatmap and weekly_study_minutes without any client-side computation.

activity_typeCreated whenClosed when

flashcardUser opens deck studyDeck complete / user exits
chat(optional) Session createdSession deleted or manually ended

Cross-Cutting: AI Provider Abstraction

All six modules share a single entry point into the AI layer: _call_llm(system_prompt, user_prompt, max_tokens). This function dispatches to the configured provider and applies the retry policy transparently.

async def _call_llm(system, user, max_tokens=2048) -> str:
    for attempt in range(1, MAX_RETRIES + 1):
        try:
            if settings.AI_PROVIDER == "watsonx":
                return await _call_watsonx(system, user, max_tokens)
            else:
                return await _call_openai(system, user, max_tokens)
        except Exception as exc:
            if attempt < MAX_RETRIES:
                await asyncio.sleep(RETRY_BASE ** attempt)
    raise RuntimeError("AI provider unavailable")
ConcernOpenAIIBM watsonx.ai
ClientAsync AsyncOpenAISync SDK → asyncio.to_thread()
History formatStructured messages[] arrayFlat [ROLE]: text string
Model configOPENAI_MODEL (default: gpt-4o-mini)WATSONX_MODEL (default: llama-3-3-70b)
AuthOPENAI_API_KEYWATSONX_API_KEY + WATSONX_PROJECT_ID
JSON fencesHandled by _extract_json()Handled by _extract_json()
Adding a third provider (e.g., Anthropic Claude, Mistral) requires only: (1) add a new _call_anthropic() function, (2) add "anthropic" to the AI_PROVIDER validator, (3) add a branch in _call_llm(). All six feature modules are unaffected.

study_sessions id, user_id, activity_type, resource_id, duration_minutes, score, ended_at Analytics, Recommendations

Key Design Decisions

  • UUIDs everywhere — no integer sequences, making all IDs safe to expose in URLs.
  • JSON columns for questions[], answers[], key_concepts[] — avoids a separate join table while keeping data queryable in PostgreSQL.
  • SET NULL on document delete for quizzes, decks, and chat sessions — preserves quiz/deck history even after the source file is removed.
  • CASCADE delete from user → all owned data — a single row deletion in users cleans up everything.
  • Composite indexes on (owner_id, created_at) for list queries to avoid full table scans.

Extension Points & Future Work

AI Recommendations Endpoint

Add POST /analytics/recommendations — use explain_concept() to generate a personalized study plan for documents with avg_quiz_score < 60 and list due flashcard decks by ease factor.

Embedding-Based Search

Store OpenAI embeddings of document chunks in a pgvector column. Enable semantic similarity search across all uploaded material — both for the chatbot's retrieval and cross-document recommendation.

Streaming Chat Responses

Replace the single-response chat_with_tutor() with an AsyncGenerator that streams tokens via Server-Sent Events. Both OpenAI and watsonx support streaming; the frontend textarea can render tokens as they arrive.

Multi-Document Chat Context

Allow a chat session to link multiple documents. The route would concatenate the top-k retrieved chunks (via embedding cosine similarity) instead of the full text of one document.

Per-Question Weak-Topic Tags

Add a topic_tag field to each question in the Quiz.questions JSON. Track incorrect answers by tag across attempts. Surface tag-level accuracy in analytics to pinpoint sub-topics, not just documents.

Adaptive Quiz Difficulty

Read the student's rolling 7-day average score per document and automatically adjust the difficulty parameter passed to generate_quiz(): promote to hard after 80%+, drop to easy after consecutive failures.

Deployment Checklist

  • Set AI_PROVIDER, API keys, and SECRET_KEY in .env before first run.
  • Run docker compose up --build — starts FastAPI + PostgreSQL with health checks and named volumes.
  • Run alembic upgrade head inside the container to apply schema migrations.
  • The UPLOAD_DIR volume must be persisted across container restarts (already configured in docker-compose.yml).
  • For production, set MAX_FILE_SIZE_MB, configure an object store (S3/COS) in document_service.py, and add a rate-limit middleware on AI-calling routes.
